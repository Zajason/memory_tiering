# Prefetch model and window ladder, 15 November 2026

Status: **complete, all six workloads.** bc, sssp and cc finished on 15 November.
bfs (200 trials), tc and pr were killed by a machine shutdown at 21:30 that day,
with the ladder unwritten because it was only emitted at exit. The tool now
rewrites a `.ladder.csv` snapshot every 32 epochs (atomic rename); the three were
relaunched at 01:30 on 16 November and finished at 03:39 (pr), 05:14 (tc) and
05:59 (bfs). Their killed partials are kept in
`results/prefetch-ladder-2026-11-15/interrupted-2130/`. The relaunched runs use
the snapshotting build, so their tool hash differs from the first three; the
measurement code path is unchanged. Numbers:
`results/prefetch-ladder-2026-11-15/SCORECARD.md`, regenerated by
`src/analysis/plot_prefetch_ladder.py`.

## Why

Under whole-execution collection our cc and bfs pages were *sparser* than M5's
(cc P(<=16) 0.41 against 0.20). A longer window cannot fix that: whole-execution
is already the longest window there is. Something had to be making M5's pages
denser than our model can produce, and the audit had already named the missing
piece: the model had no hardware prefetching. A prefetch is a read at the CXL
device like any other, so a demand-only model under-counts touched words.

## What changed in the instrument

1. `src/profiler/pintool/prefetcher.hpp` -- the L2 spatial (adjacent-line) and
   streamer prefetchers, with every constant taken from Intel's Optimization
   Reference Manual (128 B pairs; one stream per 4 KB page, 32 streams; two
   prefetches per L2 lookup; at most 20 lines ahead; never across a page). One
   value is not in the manual and is an assumption: how many monotone requests
   confirm a stream (`-pf_confirm`, default 2). Off by default (`-prefetch 1`).
2. `paired_observer.hpp` -- a window ladder. Level j ORs two completed level j-1
   windows, so one run yields the histogram for every window of 10M x 2^j device
   events up to the whole run. No window is chosen per benchmark.
3. `src/analysis/ladder_report.py` -- scores every level and reports the
   leave-one-out error: one window for all benchmarks, chosen using the *other*
   benchmarks only. That is the number to quote. The per-benchmark best level is
   printed as a fitted lower bound and must not be quoted as agreement.

Checks: `test_ladder_prefetch.cpp` (ladder level equals brute-force OR and equals
"whole" when it spans the run; prefetches never cross a page, never exceed 20
lines or 3 requests per lookup; isolated touches fetch only the pair line).

## Protocol (declared before the runs)

Real inputs of the fidelity campaign, one thread, 10-way LLC, timed kernel,
10M-event epochs pooled across trials, prefetch on, confirm = 2. Trials: bfs 200
(artifact command); cc 3 (deterministic across trials -- the 200-trial control
gave an identical whole-run curve); bc 4 and sssp 8 instead of the artifact's 100
and 200, which would take days under Pin -- enough for the ladder to reach its
top level, but a shortfall against the artifact all the same; tc 1; pr 1.

### A common event window fails; a common time window does not

The declared protocol scored one window, in device events, for all benchmarks,
chosen leave-one-out. With all six in, that gives a mean of 0.197 and makes tc
*worse* than the old headline (0.349 -> 0.387): the others want hundreds of
millions of events, while tc produces only 380M events in its entire run and
matches M5 at 20M.

The workloads differ about 300-fold in device events per instruction:

| workload | instructions per 10M device events |
|---|---|
| pr | 74M |
| bc | 158M |
| sssp | 178M |
| cc | 296M |
| bfs | 328M |
| tc | 21.9B |

A profiler interval is a time, not an event count. Converting each ladder level
to the instructions it spans (total instructions / completed epochs x 2^j) and
asking for one window *in instructions* for all benchmarks, again chosen
leave-one-out over a quarter-octave grid from 1B to 2048B (ties resolved to the
middle of the plateau), every held-out benchmark gets 45-54 billion instructions
and the mean error is 0.110. `plot_prefetch_ladder.py` computes both scorings.

What can and cannot be said:

- **The unit was chosen after seeing the data.** The switch from events to
  instructions was made once the event window was seen to fail on tc. The length
  is leave-one-out; the unit is a post-hoc modelling decision with a physical
  justification, and should be presented as such.
- **cc is the prefetcher's gain and is not window-limited.** The error halves
  and is flat across every level (0.237-0.249). The first three points sit within
  0.03 of M5; the remaining error is at N = 48 (we have 37% of pages above 48
  words, M5 has 61%). confirm = 1 gives 0.234, so the assumed parameter is not
  carrying the result.
- **bfs needs both.** Prefetching moves its whole-run error from 0.584 to 0.236;
  the time window then takes it to 0.079.
- **bc and sssp gain from scope, not from prefetching.** Their whole-run error
  was already 0.14 / 0.11. At the common window our curves are essentially zero
  at every N, i.e. slightly denser than M5; the error is M5's own value at N = 48.
- **tc is the benchmark that discriminates.** It is the only one whose error
  rises on both sides of the chosen window (0.256 at 22B instructions, 0.062 at
  44B, 0.158 at 88B).
- **The window is resolved to a factor of two.** Levels double, so roughly
  30-60 billion instructions select the same levels for every benchmark.
- Instructions are single-thread Pin instructions standing in for wall time on a
  20-core machine. M5's own collection interval is still unpublished; this does
  not recover it, it shows that one time-like interval is consistent with all
  six curves.

## Not addressed

Kernel-side traffic (the `read()` copy that loads the graph, page zeroing) is
still invisible to Pin. Thread count stays at one. The L1 prefetchers and
LLC-only far prefetches are not modelled, so the model still fetches less than
real hardware -- consistent with the residual cc error being on the dense side.
